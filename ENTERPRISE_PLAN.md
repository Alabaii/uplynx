# Архитектура двух редакций: Team и Enterprise

Статус реализации (обновлено 2026-07-08):
- **Фаза A — реализована**: организации в схеме данных, миграция 0002 с бэкфиллом, членство при регистрации, `/auth/me` с блоком organization.
- **Фаза B — реализована**: RBAC-роли (viewer/member/admin/owner), общий воркспейс организации (мониторы/конфиг/Telegram по `org_id`), эндпоинты `/orgs` и страница Team, командные алерты, org_id в JWT, миграция 0003.
- **Фаза C — реализована частично** (C-lite): ретеншен `RETENTION_DAYS` с суточным роллапом в `uptime_daily` (миграция 0004), batch-эндпоинт `GET /monitors/uptime`, честные метрики на дашборде. Остались: партиционирование, fair scheduling, квоты per-org — ближе к реальной нагрузке.
- Фаза D — спроектирована, не начата.

Решения зафиксированы с владельцем продукта 2026-07-08:

- **Одна кодовая база**, режим выбирается переменной окружения `DEPLOYMENT_MODE=team|enterprise`.
- **Мультитенантность на уровне приложения**: одна инсталляция, одна БД, сущность «организация», данные изолируются фильтрацией по `org_id` (модель Grafana/GitLab).
- Enterprise-режим сейчас только проектируется; в коде уже реализованы `DEPLOYMENT_MODE` и лимиты team-режима.

---

## 1. Две редакции

| | Team (лёгкая) | Enterprise (большая) |
|---|---|---|
| Аудитория | Одна команда ≤ 20 человек | Много команд на общем сервере |
| Мониторы | ≤ 100 | Без встроенного лимита (квоты на организацию) |
| Организации | Одна неявная («default») | Много, с ролями и приглашениями |
| Развёртывание | `docker-compose up --build` | docker-compose с репликами воркеров; при росте — Kubernetes/Helm |
| БД | PostgreSQL, один инстанс | PostgreSQL + партиционирование `check_results`, реплики на чтение при необходимости |
| Очередь | RabbitMQ, по 1 воркеру | RabbitMQ-кластер, N воркеров каждого типа |
| Лимиты | Жёсткие из env (`TEAM_MAX_USERS=20`, `TEAM_MAX_MONITORS=100`) | Квоты per-org в БД |

Ключевой принцип: **team-режим — это enterprise-режим с одной организацией и включёнными лимитами**. Никакой отдельной ветки кода; отличия — только флаги и то, какие экраны/эндпоинты активны.

## 2. Модель данных (целевая)

Добавляются две сущности, существующие расширяются:

```
Organization:
  - id
  - name
  - slug
  - created_at
  - quota_monitors (nullable — null = без лимита)
  - quota_members (nullable)

OrgMember:
  - org_id (FK)
  - user_id (FK)
  - role: owner | admin | member | viewer
  - created_at
  - UNIQUE(org_id, user_id)
```

Миграция существующих таблиц:

- `monitors.org_id` (FK, NOT NULL) — вместо привязки только к `user_id`. `user_id` остаётся как «кто создал».
- `config_versions.org_id` — конфиг становится **атрибутом организации, а не пользователя**. Это главное семантическое изменение: сейчас у каждого пользователя свой конфиг, что в командной работе противоречит идее «конфиг = источник правды» (два человека одной команды видят разные конфиги). В team-режиме все состоят в организации `default`, значит конфиг общий для команды — это и есть правильное поведение для мониторинга.
- `telegram_integrations.org_id` — алерты командные, не личные. Один канал/чат на организацию (плюс опционально личные подписки позже).
- Существующие таблицы `groups`/`group_members` (PRD 5.2) упраздняются в пользу `organizations`/`org_members` — они дублируют друг друга, а реализованы не были.

Миграция данных при апгрейде team → enterprise не нужна: уже в team-режиме всё привязано к организации `default`. Апгрейд = смена env-переменной.

## 3. Изоляция и авторизация

- JWT получает claim `org_id` (активная организация) — при переключении организации выпускается новый токен.
- Все запросы к данным проходят через зависимость `get_current_org_member`, которая: валидирует JWT → проверяет членство → отдаёт `(user, org, role)`. Каждый SQL-запрос фильтруется по `org_id`. Прямых запросов «по user_id» к мониторам не остаётся.
- Роли:
  - `viewer` — читает дашборд/историю;
  - `member` — CRUD мониторов, редактирование конфига;
  - `admin` — Telegram-интеграция, приглашения, откат конфига;
  - `owner` — квоты, удаление организации, передача владения.
- Защита в глубину (опционально, фаза 2): PostgreSQL Row-Level Security по `org_id` как страховка от ошибок фильтрации в коде.

## 4. Планировщик и воркеры под нагрузкой

Уже сделано в текущей итерации: `SELECT ... FOR UPDATE SKIP LOCKED` в scheduler (можно запускать несколько реплик), переиспользование соединения RabbitMQ, обработка ошибок в консьюмерах.

Для enterprise дополнительно:

1. **Горизонтальное масштабирование воркеров** — уже возможно: `docker compose up --scale worker-http=4 --scale worker-browser=2`. Очереди конкурентные, `prefetch_count=1` гарантирует честное распределение.
2. **Fair scheduling между организациями**: чтобы одна организация с тысячами мониторов не выедала очередь, scheduler публикует батчами с round-robin по `org_id` (сортировка `ORDER BY org_id, next_run_at` с лимитом на организацию за тик).
3. **Партиционирование `check_results`** по месяцам (declarative partitioning) — таблица растёт быстрее всех; удаление старых партиций вместо `DELETE` решает и ретеншен (PRD 5.9: год хранения, потом расчёт uptime % и экспорт).
4. **Отдельный процесс-архиватор** (cron-контейнер или periodic task): считает дневные агрегаты uptime в `uptime_daily (org_id, monitor_id, date, uptime_pct, avg_response_ms)` — дашборд читает агрегаты, а не сканирует сырые результаты.
5. **Браузерные воркеры** — самый дорогой ресурс: квота `browser_checks` per-org и отдельный autoscaling (по глубине очереди).

## 5. Конфиг-система в мультикомандном мире

- `GET/POST /config` работают в скоупе активной организации.
- Версионирование остаётся (`config_versions.org_id`), diff/rollback — на уровне организации.
- Конкурентное редактирование: optimistic locking — клиент шлёт `base_version`, при расхождении 409 с diff (в UI уже есть diff-механика).

## 6. Поверхность API (дельта)

```
GET    /api/v1/meta                    — режим и лимиты (уже реализовано)
GET    /api/v1/orgs                    — мои организации
POST   /api/v1/orgs                    — создать (enterprise)
POST   /api/v1/orgs/{id}/invites       — пригласить по email (enterprise)
POST   /api/v1/orgs/{id}/switch        — переключить активную организацию (новый JWT)
GET    /api/v1/orgs/{id}/members       — участники, роли
PATCH  /api/v1/orgs/{id}/members/{uid} — смена роли (admin+)
```

В team-режиме организационные эндпоинты возвращают 404/403, UI-раздел скрыт — по флагу из `/meta`.

## 7. Фронтенд (дельта)

- При старте приложение читает `/api/v1/meta`; `deployment_mode` кладётся в контекст.
- Enterprise: переключатель организации в сайдбаре (текущая карточка воркспейса становится реальной), страница участников/ролей, экран приглашения.
- Team: всё как сейчас, плюс индикатор потребления лимитов («87/100 мониторов»).

## 8. Развёртывание

- **Team**: текущий `docker-compose up --build` — ничего не меняется, это главная ценность лёгкой редакции.
- **Enterprise, ступень 1**: тот же compose + `--scale`, внешний PostgreSQL/RabbitMQ по env-переменным, reverse-proxy с TLS.
- **Enterprise, ступень 2** (при реальной необходимости): Helm-чарт; scheduler — Deployment с 2 репликами (SKIP LOCKED уже позволяет), воркеры — HPA по глубине очереди (KEDA + RabbitMQ scaler).

## 9. Порядок внедрения (когда решим делать)

1. **Фаза A — фундамент** (~схема БД): таблицы `organizations`/`org_members`, `org_id` во всех доменных таблицах, миграция «создать default-организацию и привязать всё существующее», зависимость `get_current_org_member`. Team-режим внешне не меняется.
2. **Фаза B — роли и члены**: эндпоинты организаций/участников/приглашений, org_id в JWT, RBAC-проверки. UI участников.
3. **Фаза C — масштаб**: партиционирование результатов, uptime-агрегаты, fair scheduling, квоты per-org.
4. **Фаза D — полировка enterprise**: RLS, аудит-лог действий, SSO (OIDC) при необходимости.

Фазу A можно делать без риска для team-редакции — она чисто аддитивна, а «default»-организация делает поведение неотличимым от текущего.

## 10. Отклонения от PRD, зафиксированные этим документом

- PRD 5.2 «Groups/GroupMember» заменяется на Organizations/OrgMembers (группы не были реализованы; организации решают ту же задачу плюс тенантность).
- PRD 2.3 «у каждого пользователя свой config» меняется на «у каждой организации свой config» — для командного мониторинга личные конфиги противоречат сути продукта.
